Documento madre canónicoBloque 0.5. Encuadre
Capa 1 v2.1 de EVEDiseño detallado para continuación acoplable posterior al Bloque 0, conexión con Codex, catálogo operativo, UI y persistencia
Versión del documento: revisión actor-céntrica aprobada | Base estructural: Diseno_Formal_Capa1_v2_1_Unificado | Base de redacción operativa: Marco de Trabajo y Catálogo de Preguntas v2.1 - Bloque 0.5 (Encuadre)
Alcance: desarrollo exhaustivo del Bloque 0.5 como pieza canónica autónoma, diseñada para pegarse a continuación del Bloque 0 y para trabajar con una muestra funcional limitada de informantes. El bloque conserva la perspectiva situada de cada persona y pospone la integración sistémica para el cruce entre escenas, roles y bloques.
Criterio rector: este documento no sintetiza ni reemplaza silenciosamente evidencia. Explicita arquitectura, preguntas, lógica de despliegue, variables, proveniencia, consistencia, persistencia, trazabilidad y salida técnica. La complejidad sistémica se resuelve detrás de la interfaz; el usuario recibe lenguaje de trabajo, help text breve y ejemplos de trinchera.
0. Inicio de acoplamiento con el Bloque 0
Este bloque comienza exactamente donde termina el Bloque 0. El Bloque 0 deja una escena ya nombrada, delimitada y con una referencia a quién recibe directamente lo que el usuario hace; el Bloque 0.5 toma esa escena y la sitúa en un contexto mayor sin pedirle al informante que reconstruya por sí solo toda la empresa.
La continuidad de ensamblaje se lee así: actividad declarada por el usuario -> escena operativa regulada anclada por el Bloque 0 -> perspectiva funcional situada en el Bloque 0.5 -> reconstrucción causal posterior en Bloques 1 a 6 -> integración entre informantes y preclasificación posterior. Lo que una persona no puede confirmar se conserva como límite de conocimiento, no como error del usuario.
Instrucción de integración documental: este bloque mantiene la misma estructura madre y los mismos códigos canónicos. El rediseño cambia semántica visible, proveniencia y lógica de despliegue allí donde era necesario, pero no crea códigos nuevos ni presupone datos maestros organizacionales que el cliente no haya entregado.

2. Decisión metodológica central del Bloque 0.5
El Bloque 0.5 existe para ampliar la mirada sin romper la epistemología actor-céntrica. La muestra prevista es deliberadamente funcional y limitada: aproximadamente 16 informantes, con dos roles funcionales en cada una de ocho áreas de gestión comunes. Por diseño, ninguno de ellos tiene que conocer por completo la empresa; juntos aportan variedad suficiente para que EVE reconstruya relaciones que una sola persona no puede ver.
Actor-céntrico no significa localista. Cada persona responde desde su posición funcional y EVE distingue entre lo que observa directamente, lo que conoce por su rol, lo que estima y lo que no puede confirmar. La integración sistémica ocurre después, al cruzar informantes, escenas y bloques. Una diferencia entre dos respuestas no se declara contradicción de inmediato: primero puede ser una diferencia de frontera, nivel de recursión o punto de observación.
El receptor inmediato capturado en Bloque 0 se usa como ancla, no como sinónimo automático de beneficiario. Bloque 0.5 pregunta qué beneficio y qué daño alcanza a reconocer el informante, qué puede avanzar gracias a la actividad, en qué trabajo mayor la ubica y cómo se ordena bajo presión. No le pide identificar objetivamente al 'beneficiario final' ni formular una necesidad empresarial abstracta que quizá no puede observar.
La lógica es de subsidiariedad epistemológica: la información se captura lo más cerca posible de donde se vive, pero permanece conectada hacia arriba mediante proveniencia, aclaración y cruce entre observadores. Así EVE aumenta variedad informacional sin trasladar al usuario la carga de pensar como arquitecto organizacional.

4. Criterios de diseño de las preguntas del Bloque 0.5
Las preguntas deben ampliar el encuadre de la escena sin pedir al informante una visión omnisciente del proceso completo.
La redacción visible debe usar lenguaje de trinchera. Una pregunta contiene una idea; el help text solo desambigua y se mantiene corto.
Cada pregunta visible o aclaración incluye al menos tres ejemplos operativos claros. Los ejemplos enseñan la lógica sin exponer jerga VSM, PM o arquitectura organizacional.
Beneficiario, afectado, proceso mayor y siguiente avance se interpretan como perspectiva funcional situada. EVE registra desde dónde se conoce cada respuesta cuando la pregunta excede la observación inmediata.
0.5.1_rel se conserva como código canónico, pero deja de ser pregunta visible: se deriva internamente y solo abre 0.5.A si la relación no puede resolverse.
0.5.1b deja el flujo base. Solo aparece cuando existe una asimetría relevante entre valor y daño que las respuestas anteriores no alcanzan a explicar.
La UX usa opciones fijas portables, texto libre corto y contexto ya capturado por EVE. No presupone listas maestras de áreas, roles o procesos que el cliente no haya entregado.
Las diferencias entre informantes se preservan como perspectivas antes de declararse contradicción. El bloque deja huellas para PM y lectura VSM posterior, pero no cierra misión, diagnóstico ni clasificación.

Normalización contractual adicional: field_type define la naturaleza del control UI; answer_mode conserva el enum técnico estable; ui_answer_mode_label conserva la lectura humana del diseño; y allows_free_text debe distinguir entre no, yes o conditional. 8. Lógica de despliegue UI por pregunta
0.5.1 y 0.5.1a. Se muestran como una díada consecutiva. La UI recupera como contexto a quién recibe directamente lo que el usuario hace en Bloque 0, de modo que la pregunta pueda decir 'En esta actividad le entregas a X...' sin obligar a recordar. Las opciones son fijas y portables.
0.5.1_rel. No aparece al usuario. EVE compara las respuestas de 0.5.1 y 0.5.1a y deriva same_entity, different_entities o unresolved_relation. Si la identidad no puede resolverse sin adivinar, se conserva unresolved_relation y puede abrirse 0.5.A.
0.5.1b. Sale del flujo base. Solo aparece cuando beneficiario y afectado son distintos y además existe una necesidad real de explicar cómo se reparte el beneficio y el problema. La diferencia por sí sola no justifica otra pregunta.
0.5.1c y 0.5.1d. Forman una díada simple: primero qué puede hacer o resolver quien se beneficia; después, cómo contribuye la actividad a que eso ocurra. La UI evita términos como 'necesidad final', 'primaria', 'soporte', 'regulación' o etiquetas VSM.
0.5.2. Se presenta como campo breve: '¿Cómo le llaman ustedes al trabajo o proceso más grande del que forma parte esta actividad?'. Se conserva el lenguaje local del informante y no se le obliga a escoger una etiqueta corporativa predefinida.
0.5.3. Campo abierto guiado: 'Cuando esto queda bien hecho, ¿qué puede avanzar después?'. Si el usuario repite su propia tarea o entregable, se abre 0.5.C.
0.5.4 y 0.5.4a. Se muestran como par: qué pone esta actividad primero y qué hace soltarla una vez iniciada. Las opciones hablan de jefe, cliente, fecha/sistema, regla, acuerdo, emergencia o decisión local; la lectura regulatoria queda detrás.
0.5.A-0.5.C y base de conocimiento. Las aclaraciones aparecen solo por flags. En 0.5.1, 0.5.1a, 0.5.2 y 0.5.3 puede aparecer al pie un microcontrol de un toque: Lo veo directamente / Lo conozco por mi rol / Es mi mejor estimación / No lo puedo confirmar. No abre una pantalla nueva ni cuenta como pregunta de contenido.
8.A. Orden base de despliegue UI
Orden base visible: 0.5.1 -> 0.5.1a -> 0.5.1c -> 0.5.1d -> 0.5.2 -> 0.5.3 -> 0.5.4 -> 0.5.4a. Entre 0.5.1a y 0.5.1c EVE ejecuta internamente 0.5.1_rel. 0.5.1b solo entra por flag de asimetría que requiere detalle.
Aclaraciones: 0.5.A puede entrar si 0.5.1_rel queda unresolved_relation; 0.5.B si 0.5.2 se queda en la propia tarea o es demasiado vaga; 0.5.C si 0.5.3 repite el entregable o no identifica qué avanza después.
Contrato de implementación: se conservan los mismos códigos canónicos. Cambia el estatus visible de 0.5.1_rel y 0.5.1b, no su identidad. El microcontrol knowledge_basis es proveniencia de la respuesta, no un nuevo question_code.
9. Lógica secuencial interna del Bloque 0.5
0.5.1 captura quién termina beneficiándose principalmente según lo que el informante conoce, usando el receptor inmediato del Bloque 0 como ancla y no como respuesta predeterminada.
0.5.1a captura quién termina viéndose más afectado cuando la actividad falla, se retrasa o no ocurre, también como perspectiva situada.
0.5.1_rel compara internamente ambos polos. Solo deriva same_entity o different_entities cuando existe identidad suficiente; si no, conserva unresolved_relation.
0.5.1b, cuando un flag lo justifica, explica la asimetría entre valor y daño. No se abre automáticamente porque beneficiario y afectado sean distintos.
0.5.1c captura una consecuencia observable: qué puede hacer o resolver el beneficiario gracias a que la actividad salió bien.
0.5.1d identifica cómo contribuye la actividad a ese resultado: directamente, habilitando a otros, coordinando/validando, de forma mixta o incierta.
0.5.2 pide el nombre que el informante usa para el trabajo o proceso mayor, sin imponer una taxonomía externa.
0.5.3 identifica el siguiente avance real que puede ocurrir cuando la actividad queda lista.
0.5.4 registra la fuente efectiva de prioridad normal y 0.5.4a registra lo que desplaza trabajo ya iniciado.
La base de conocimiento acompaña la evidencia cuando la pregunta rebasa la observación inmediata: direct_observation, role_based_knowledge, best_estimate o unconfirmed. No es una autoevaluación de 'claridad'; describe desde dónde sabe lo que está diciendo.

17. Relación formal con el Bloque 0 y con los bloques posteriores
El Bloque 0 entrega la escena y el receptor inmediato observado. Bloque 0.5 no vuelve a preguntar quién recibe el objeto: usa ese dato como ancla para explorar hasta dónde alcanza el conocimiento funcional del informante sobre beneficio, daño, siguiente avance y contexto mayor.
El Bloque 1 recibe un encuadre más honesto: un nombre local para el trabajo/proceso mayor, un siguiente avance y una proveniencia explícita. Si algo está unconfirmed, el gap viaja con la escena en lugar de ser rellenado por inferencia.
Bloques 3 y 4 son claves para fortalecer o corregir scene_functional_client_candidate: el receptor real, las entregas, dependencias y rutas permiten contrastar la perspectiva de 0.5 con flujo observado. Una diferencia no invalida automáticamente al informante; puede revelar una frontera distinta del sistema.
Bloque 5 hereda las fuentes de prioridad y desplazamiento para estudiar capacidad, discreción y variedad residual. Bloque 7 puede usar scene_beneficiary_enabled_outcome y scene_value_contribution_mode como huellas de preclasificación, manteniendo abierta la decisión sobre S1, S2, S3, S3*, S4, S5 y el canal algedónico.
18. Mapeo preliminar a VSM y canal algedónico
Este bloque no clasifica la escena en un sistema VSM definitivo. Un resultado que llega directamente a un beneficiario y habilita creación de valor puede ser una pista hacia S1, pero direct_value no equivale automáticamente a S1. enabling_support y regulatory_support son candidatos de soporte o regulación cuyo significado depende del sistema en foco y de evidencia posterior.
Las fuentes de prioridad, coordinación y desplazamiento aportan material para S2 y S3. S3* exige evidencia real de auditoría, verificación o acceso no filtrado y no puede inferirse solo porque prioridad formal y prioridad real difieran. S4 requiere evidencia de futuro/adaptación y S5 evidencia de identidad, política o criterios últimos; esas funciones no se inventan desde este bloque.
El canal algedónico solo cobra fuerza cuando otras evidencias muestran dolor, riesgo o escalamiento que rebasa los canales normales. Del mismo modo, que una persona decida localmente prioridades puede ser subsidiariedad saludable o sobrecarga; Bloque 0.5 conserva el hecho y deja la interpretación para el cruce con capacidad, autoridad, soporte y escalamiento.
19. Reglas de aceptación del Bloque 0.5
Queda capturado quién termina beneficiándose principalmente según lo que el informante conoce, sin presentarlo como beneficiario final objetivo.
Queda capturado quién termina viéndose más afectado y desde qué base de conocimiento se afirma.
0.5.1_rel se derivó internamente o, si no pudo resolverse, quedó explícitamente unresolved_relation y 0.5.A se usó solo cuando era necesario.
0.5.1b no apareció por defecto; solo se usó si la asimetría entre valor y daño necesitaba una explicación adicional.
Quedó descrito qué puede hacer o resolver el beneficiario gracias a la actividad y cómo contribuye la escena a que eso ocurra.
La escena quedó ubicada en un trabajo/proceso mayor usando el lenguaje del informante, sin obligarlo a escoger una etiqueta corporativa predefinida.
Existe un siguiente avance identificable o un gap explícito; no se confunde el entregable propio con lo que puede avanzar después.
La fuente de prioridad normal y la fuente que desplaza trabajo ya iniciado quedaron registradas con lenguaje operativo.
Las respuestas que exceden observación inmediata conservan knowledge_basis; unconfirmed se trata como gap de cobertura, no como falla del usuario.
Puede consolidarse un scene_frame_bundle suficiente para pasar a Bloque 1 y dejar un scene_functional_client_candidate trazable, no una verdad cerrada desde una sola respuesta.
Las diferencias entre informantes se preservan como perspective_divergence antes de cualquier declaración de contradicción.

21. Nota final de diseño
