1. Propósito, autoridad y frontera
El propósito de esta especificación es convertir el diseño operativo del Panel de Control EVE en una pantalla implementable para el consultor experto, sin duplicar la arquitectura de negocio ni desplazar la autoridad del Runtime, Capa 1.0 o Producción Paralela.
1.1 Cadena documental de implementación
Diseno_Panel_Control_EVE_Runtime_40_20_MBA_Ajustado_v2_RolFuncional  -> Especificacion_UI_FrontEnd_Panel_Control_Consultor_EVE_v1  -> Contrato BFF/API  -> Fixture de datos  -> Implementacion en /admin/consultant-control-panel
1.2 Decisiones no negociables
Decisión
Aplicación en la pantalla
Prohibición asociada
Cabina de observación y gobierno
La UI presenta estado, causalidad, readiness, gaps, timers, trazabilidad y elegibilidad de descargas.
No convertirse en motor diagnóstico ni en editor de evidencia.
Capa 1.0 y Producción Paralela operativas
Son las únicas líneas mostradas como ejecución de plataforma.
No presentar Capa 2.0, 2.5 o 3.0 como módulos automáticos.
Runtime 40+20 por actividad primaria
La UI muestra 40 bases resueltas y 20 causales evaluadas por activity_runtime_run.
No representar el Runtime como encuesta lineal ni cerrar solo por conteo.
Conformance antes de consistency
Producción Paralela muestra la secuencia de QA y bloquea export cuando ACA no está Satisfied.
No alinear modelos ni habilitar export de forma cosmética.
user_id distinto de role_runtime_session
Un usuario físico se expande en uno o más perfiles funcionales internos.
No crear logins paralelos ni colgar runs solo de user_id.
Gate > acción manual
La UI solo expone acciones que el BFF declare permitidas.
No forzar ready ni saltar B0/B2/B3/B7, SEM o PST.
Evidencia inmutable
La pantalla muestra evidencia y revisiones como solo lectura.
No editar respuestas, borrar versiones ni crear hechos desde texto libre.
1.3 Fuera de alcance
Rediseñar el Runtime 40+20, el Catálogo Madre o el Catálogo Runtime.
Crear nuevas bases B0-Q01..B7-Q40 o causales C21+.
Automatizar transducción Capa 2.0, agregación Capa 2.5 o síntesis Capa 3.0.
Implementar acceso directo del navegador a Supabase o exponer service_role.
Definir nombres reales de archivos, imports o componentes del repositorio existente sin inspección del repo.
Generar el fixture productivo o el paquete Codex/Cursor en este mismo artefacto.
2. Barrido rector y decisiones derivadas
El diseño de pantalla se deriva del Marco Estructural maestro y se contrasta contra los artefactos rectores. La siguiente matriz explicita qué autoridad se conserva y qué decisión UI resulta.
Fuente rectora
Autoridad conservada
Decisión UI derivada
Marco Estructural maestro
Stack documental, frontera Capa 1.0/Producción Paralela, Gate > Chip, seguridad y auditoría.
La pantalla se organiza como control shadow: observa, no sustituye los motores ni promueve estados sin gate.
Fundamentals of Business Architecture Modeling
PM, MoC, PF, OLC; conformance antes de consistencia; Process State y causalidad.
Cada estado visible debe corresponder a Object[State], evento, timer, proceso responsable o bloqueo.
MBA EVE v1.1 B3/B7
Procesos P-CORE/P-SUP, objetos, OLC, target states, B3/B7 y exportación.
La UI presenta milestones y objetos; export solo desde ACA [Satisfied].
Diseño Capa 1.0
SCR, EvidenceBundle, evidencia, derivación, gaps y readiness.
Contexto, evidencia, variable, gap y readiness se distinguen visualmente.
Diseño Producción Paralela
MDSB, candidatos, facts, registries, IR, QA y export.
Descargas y estados siguen la secuencia fuente -> candidato -> inventario -> IR -> QA -> export.
Catálogo Madre Capa 1 v1.0
164 nodos canónicos, rutas críticas, genealogía y frontera B7.
La UI nunca expone los 164 nodos como entrevista; usa source refs en detalle/auditoría.
Catálogo Runtime v1.1.1 XLSX
40 bases, 20 causales, subcampos, variables, branching, gates, readiness y QA.
Las matrices 40/20 consumen registros operacionales; no se construyen desde narrativa.
Runtime técnico ejecutable v1.0.1
Entidades, estados, API lógica, idempotencia, recomputación, seguridad y audit trail.
El BFF compone view models; el navegador no consulta entidades crudas ni base de datos.
Diseño del Panel v2 RolFuncional
Cabecera, navegación, vistas, acciones, descargas, alcance manual downstream y multirrol.
Define la estructura de componentes y la jerarquía empresa -> caso -> usuario -> rol -> actividad -> run.
VSM / Viplan
Autorregulación, variedad residual, coordinación y autoridad distribuida.
El panel informa desviaciones y habilita corrección gobernada; no centraliza control extrínseco sin auditabilidad.
AHE
Causalidad humana recursiva sin psicologizar individuos.
La pantalla no muestra juicios de actitud/cultura; solo materialidad, interacción y trazabilidad cuando corresponda.
Instrucciones MMABP + EVE / Tabla de inconsistencias
Disciplina de conformance, consistencia y patologías.
El panel muestra hallazgos técnicos; no emite diagnóstico EVE automático.
Regla epistemológica de la UILa pantalla puede resumir y navegar información gobernada, pero no puede elevar contexto a evidencia, inferencia a hecho, candidato a inventario, inventario a IR ni IR a exportación sin el estado y gate correspondientes.

9. Contrato BFF/API
Frontera técnicaEl front-end consume exclusivamente endpoints BFF bajo /api/eve/consultant/control-panel. El BFF resuelve autenticación, tenancy, scope, composición, normalización de estados y redacción de campos. No se permite acceso directo del navegador a tablas o vistas Supabase.
9.1 Convenciones
Convención
Regla
Método
GET para lectura; POST solo en endpoints futuros auditados.
Scope
case_id obligatorio; otros IDs opcionales y validados como descendientes del case.
Envelope
request_id, generated_at, data, meta, errors.
Versionado
Header X-EVE-Contract-Version: 1.0; cambios incompatibles requieren nueva versión.
Cache
private, no-store para datos sensibles por defecto; ETag opcional para read model.
Paginación
cursor opaco, limit máximo definido por BFF.
Fechas
ISO-8601 UTC; UI localiza para presentación.
Enums
Valores canónicos del backend; UI usa mapping centralizado.
Nulos
null significa desconocido/no producido; nunca convertir automáticamente en false.
Redacción
No enviar campos innecesarios, secretos, service_role ni datos fuera de scope.

11. Seguridad, autoridad y auditoría
11.1 Reglas de frontera
Regla
Implementación obligatoria
No cliente
La ruta vive bajo layout/admin guard y no se incluye en navegación de cliente.
No service_role en front-end
Ningún bundle, env público, payload o source map contiene service_role.
No Supabase directo
El browser no instancia cliente privilegiado ni consulta tablas/vistas del Runtime.
BFF como front door
Toda lectura y futura mutación pasa por el BFF autorizado.
Tenancy
El BFF restringe empresa/caso; no acepta scope por confianza en query params.
Scope recursivo
user, role, activity y run deben pertenecer causalmente al case autorizado.
Mínimo privilegio
El response omite campos no requeridos y secretos.
Auditabilidad
Acciones futuras registran actor, razón, scope, prior/new value, timestamp e idempotency key.
Evidencia inmutable
Correcciones se representan como revisiones/superseded; la UI no borra historia.
Rutas críticas
Cambios B0/B2/B3/B7 exigen audit trail y recomputación.

12.1 Política de reintentos
GET idempotentes: máximo 2 reintentos con backoff para errores de red/5xx; no reintentar 4xx.
No hacer polling global agresivo. Refrescar state al cambiar selección y usar refresh manual.
Traza y auditoría usan paginación; no descargar todo el historial al abrir pantalla.
Una futura mutación nunca se reintenta sin idempotency_key.

Las reglas siguientes precisan descargas manuales downstream, estado no ejecutable de acciones futuras, alerta multirrol ROLE_ASSIGNMENT_GAP, vista inicial exacta y criterios de aceptación adicionales. Cuando exista tensión entre la redacción previa y esta adenda, esta adenda debe leerse como precisión operacional v1.1, no como borrado del texto anterior.

17. Descargas manuales downstream: insumos, plantillas y resultados externos
Regla de frontera. La plataforma opera Capa 1.0, Runtime 40+20 y Producción Paralela. Capa 2.0, Capa 2.5 y Capa 3.0 no se ejecutan automáticamente en la plataforma en esta versión. Por tanto, las descargas downstream deben presentarse como insumos o plantillas para trabajo manual experto, no como resultados producidos por motor automático.

Plantilla manual downstream
Workbook o estructura vacía/prellenada parcialmente para que el consultor trabaje fuera del motor automático.
Columnas esperadas, referencias de evidencia, campos de análisis manual, secciones de validación y trazabilidad.
No es diagnóstico, no es película causal final y no es síntesis experta cerrada.
Resultado manual externo

Solo puede aparecer si existe función futura de upload, versionado, validación y auditoría.
No debe mostrarse como disponible en v1.0/v1.1 si no existe módulo de carga y control.

17.2 Regla de no confusión entre insumo y resultado manual
La plataforma descarga insumos manuales y plantillas downstream.No descarga resultados manuales de Capa 2.0, Capa 2.5 o Capa 3.0 salvo que exista un módulo futuro de carga, versionado, validación y auditoría.Todo workbook downstream debe declarar: source_object, source_state, generated_from, manual_use_scope, restrictions y non_automatic_execution_flag = true.

19. ROLE_ASSIGNMENT_GAP: alerta para usuario multirrol sin asignación estable
Definición. ROLE_ASSIGNMENT_GAP aparece cuando un user_id físico declara o evidencia múltiples áreas/roles, pero una responsabilidad o actividad de WorkMap no está asignada de forma estable a un role_runtime_session. La alerta no diagnostica autoridad ni estructura organizacional; solo protege trazabilidad funcional del runtime.
Campo
Valor esperado
alert_id
ROLE_ASSIGNMENT_GAP
severity
warning o review según impacto en selección primaria/runtime
affected_scope
case_id + user_id + responsibility_id/activity_id opcional + role_runtime_session_id si existe candidato
trigger_condition
Responsabilidad o actividad sin role_runtime_session; o assignment_status = mixed_unresolved; o multirol detectado sin confirmación.
visible_in
FunctionalHelpPanel, CompanyUserRoleMatrix, GateReadinessPanel como warning no diagnóstico, AuditTrailPanel si hubo reasignación futura.
blocks_ready
No por defecto. Bloquea solo si impide situar activity_runtime_run o cerrar evidencia necesaria para readiness.
reentry_target
WorkMap functional assignment review o Estado A si el rol declarado es insuficiente.
manual_action_future
Separar perfil funcional, fusionar perfiles, reasignar responsabilidad/actividad, solicitar manual_review.

Estado
Significado UI
Regla

20. Vista inicial exacta de la pantalla
Regla de primer render. Al entrar a /admin/consultant-control-panel, la pantalla debe abrir en Centro de casos con contexto de caso, readiness, matriz usuario/rol y alertas críticas. La UI no debe abrir directamente en Runtime 40/20 salvo que el selector URL incluya un run válido y el BFF lo confirme como effective_scope.
Zona inicial
Contenido obligatorio
Header persistente
Empresa, case_id, case_state, catalog_version, runtime_version, selected_context, freshness y timers críticos.
CaseReadinessSummary
Readiness global, dominant_gate, open_gap_count, base/causal summary si existe selected run.
CompanyUserRoleMatrix
Usuarios físicos, role_runtime_session, actividades, runs, assignment_status y cobertura.
Alertas críticas
ROLE_ASSIGNMENT_GAP, B3_ROUTE_MISSING, PST sin timer, SEM unresolved, Causal P0 abierta, export bloqueado por ACA.
Banda de estado
READ-ONLY, request_id, effective_scope, generator status y permissions/capabilities.
21. Criterios de aceptación adicionales v1.1
Estos criterios se añaden a la sección 16 sin eliminar los criterios previos. Su objetivo es cerrar la frontera de descargas manuales downstream, multirrol y preview de acciones.
ID
Criterio adicional v1.1
DL-002
Ningún workbook manual downstream debe aparecer como evidencia producida por la plataforma ni como diagnóstico automático.
DL-003
Los workbooks Capa 2.0/2.5/3.0 deben distinguir insumo exportado, plantilla de trabajo manual, trabajo manual pendiente y resultado manual externo.
DL-004
Los artefactos Capa 2.5 y Capa 3.0 no deben requerir objetos manuales internos inexistentes para mostrarse como plantillas descargables.
ROLE-001
Cuando user_id tenga más de un role_runtime_session, la UI debe mostrar ambos niveles y no fusionar runs entre roles.
ROLE-002
Cuando exista mixed_unresolved o responsabilidad/actividad sin asignación funcional estable, la UI debe mostrar ROLE_ASSIGNMENT_GAP.
ACTION-001
ManualActionDrawer v1.1 no debe ejecutar submit real ni handlers mock en producción.
INIT-001
La vista inicial debe ser Centro de casos + CaseReadinessSummary + CompanyUserRoleMatrix + Alertas críticas.
22. Cierre v1.1
Dictamen. Con esta adenda, la especificación UI/front-end queda lista para pasar a paquete Codex/Cursor como pantalla read-only controlada. La implementación debe tratar esta versión como v1.1, conservar la ruta estable, preservar el modo solo lectura inicial, no habilitar acciones sin endpoint auditado y no presentar Capa 2.0/2.5/3.0 como ejecución automática.
