Diseño del Panel de Control Operativo EVE
Supervisión, intervención gobernada y descarga de Producción Paralela para Runtime 40+20 por actividad primaria
Campo
Valor
Versión propuesta
v1.0 de diseño funcional para implementación controlada
Sistema modelado
Plataforma EVE como sistema de producción de diagnóstico causal estructural
Unidad operativa de monitoreo
Usuario → CasoDiagnosticoEVE → Sesión → Actividad primaria → Runtime profundo 40+20 → SceneCanonicalRecord / EvidenceBundle / Producción Paralela
Frontera
El panel observa, gobierna y solicita reentry/intervención; no diagnostica, no monetiza, no inventa evidencia y no altera Capa 2.0/2.5.
Regla madre
40 base obligatorias por resolución; 20 causales evaluadas siempre y obligatorias si se activan; Producción Paralela descarga solo desde objetos/estados autorizados.
Ajuste de alcance operativo
v1.1 — Plataforma construida hasta Capa 1.0 y Producción Paralela; Capa 2.0, Capa 2.5 y Capa 3.0 quedan como paquetes descargables Excel para ejecución manual experta.
Regla de alcance de ejecución
El panel no debe presentar Capa 2.0, Capa 2.5 ni Capa 3.0 como módulos automatizados en plataforma. Debe presentar readiness, gaps, trazabilidad y descargas manuales.
Excepción operativa
Producción Paralela sí permanece como línea operativa de plataforma: inventario MMABP, QA de consistencia y generación de diagramas/código exportable, especialmente BPMN/Camunda cuando ArchitectureConsistencyAssessment está Satisfied.
1. Dictamen operativo
Decisión de diseño• El Panel de Control EVE debe operar como cabina de observación y gobierno del proceso, no como capa diagnóstica nueva.• Debe seguir la MBA de EVE: PM define procesos y target states; MoC define objetos; PF define espera, eventos, timers, rework y salidas; OLC autoriza estados.• Debe permitir intervención manual solo como reentry, aclaración, bloqueo, corrección de ruta, apertura de causal o manual review, siempre con trazabilidad.• No debe permitir que un operador convierta texto libre, prefill, satisfacción subjetiva o señal B7 en hecho estructural sin ruta canónica.

3. Principio estructural del panel
El panel debe reflejar el Process Map de EVE: P-CORE-01 gobierna el caso diagnóstico completo y recibe milestones producidos por procesos de soporte. La pantalla de control no sustituye esos procesos: visualiza estados, timers, readiness, gaps, reentry y bloqueos, y permite acciones manuales dentro de las fronteras autorizadas.
El panel debe tratar cada avance como transición Object[State]. No debe avanzar por ausencia de error. Debe existir evento, estado producido, proveniencia y operación autorizada.

4. Arquitectura de pantalla
La pantalla se diseña como una cabina con tres zonas: cabecera de caso, navegación por objetos/procesos y tablero de detalle. La cabecera fija el contexto; la navegación permite pasar de experiencia usuario a runtime, evidencia, producción paralela y QA; el detalle muestra estados y permite intervención gobernada.

7. Base Resolution Gate — 40 preguntas base
Para cada actividad primaria en runtime profundo, el panel debe mostrar las 40 interacciones base como una matriz de resolución. La matriz no significa 40 cajas de texto obligatorias; significa 40 estados obligatorios de resolución. Una base puede cerrarse por captura, confirmación, derivación canónica, cálculo interno, no aplicabilidad con evidencia, gap, reentry o manual review.

9. Causal Closure Gate — 20 causales
Las causales C01–C20 no son opcionales. El panel debe evaluarlas siempre por actividad primaria. Si la causal no se activa, debe quedar cerrada con evidencia de no activación. Si se activa, debe resolverse, enviarse a reentry, quedar como gap o manual review. Una causal activada y abierta impide ready pleno según su prioridad.

22. Adenda de desacople usuario físico vs rol funcional dentro del mismo login
Esta adenda agrega el ajuste operativo necesario para resolver el desacople entre la experiencia actual de cliente, que opera con un solo login por usuario físico, y la arquitectura EVE, que organiza el Runtime 40/20 por rol funcional. Esta adenda no elimina, resume ni reemplaza el contenido anterior del diseño del panel; lo especializa para que el Consultant Control Panel pueda observar correctamente usuarios que trabajan en más de un rol funcional dentro de la misma empresa cliente.
22.1 Regla raíz
Regla operativa: user_id no equivale a role_runtime_session.
Un usuario físico conserva un solo login. Dentro de ese login, la plataforma puede crear uno o más role_runtime_session internos. Cada responsabilidad y actividad del WorkMap debe quedar asociada a un role_runtime_session antes de iniciar Significado y Runtime 40/20, o bien quedar marcada como mixed_unresolved, reentry_required o manual_review_required si la asignación funcional no puede estabilizarse.
Concepto
Uso correcto en plataforma
Uso prohibido
user_id
Identidad técnica y sesión de acceso del participante cliente.
No debe usarse como sustituto de rol funcional.
role_runtime_session
Unidad operativa del Runtime por perspectiva funcional dentro del mismo usuario.
No debe requerir un segundo login.
responsibility_id
Responsabilidad redactada en WorkMap, asignable a un role_runtime_session.
No debe quedar sin perfil funcional si el usuario opera más de un rol.
activity_id
Actividad WorkMap que puede abrir activity_runtime_run si es primaria.
No debe perder su perfil funcional de origen.
activity_runtime_run
Ejecución del Runtime 40/20 para una actividad primaria situada en un role_runtime_session.
No debe colgar solo de user_id sin contexto funcional.
22.2 Ubicación del ajuste en el flujo existente
El ajuste no crea otra cuenta de usuario ni duplica la identidad del participante. Se inserta como asignación funcional interna entre WorkMap y Significado, o como subpaso de revisión dentro de WorkMap, conservando el flujo material existente: Login → Estado A-B → WorkMap → Significado → Preguntas por actividad.

22.5 Regla de selección primaria con usuarios multirrol
Para evitar fatiga extrema en PYMES, la regla inicial recomendada es mantener máximo 8 actividades primarias por usuario físico en una sesión estándar, distribuidas entre sus role_runtime_session según la política de señal arquitectónica y cobertura funcional. Si la operación futura autoriza más carga, se puede habilitar máximo 8 por role_runtime_session, pero eso debe ser una decisión explícita de alcance y experiencia, no una derivación automática.

22.9 Dictamen de la adenda
El ajuste resuelve el desacople entre experiencia de cliente y arquitectura EVE sin duplicar usuarios ni romper el Runtime.
